# Aeolus API, v1

JSON over HTTPS (0026). A browser opening `/` gets the web UI (0042), which uses this same API; `/` asked for as JSON returns pointers. A node you cannot view answers `404`.

**Roles** (0177): an account holds roles on folders of either tree, each a set of rights there and below: `admin`, `operator`, `manager`, `installer` and `viewer`; an owner, the super admin, may do everything everywhere. Every role views. In the tables, `viewer` is any role; `operator` and `admin` mean a role with the right that the request takes:

| Right | Is | Held by |
|---|---|---|
| `view` | seeing everything there but packets | every role |
| `administer` | locks, unlocks and breaks; the credentials the manager signs in with; the library's tunnels; built-in folders | admin |
| `configure` | settings, networks, radios, folders, services, templates | admin, operator |
| `keys` | residents' per-user keys | admin, operator, manager |
| `clients` | naming, tracing, reconnecting and blocking a client | admin, operator, manager |
| `aps` | adding, adopting, naming, moving, placing and removing an AP | admin, operator, installer |
| `ports` | an AP's own `ports` and `uplink` | admin, operator, installer |
| `actions` | locate, restart Wi-Fi, reboot, client tests, assurance rounds | admin, operator, installer |
| `capture` | packet captures, and what they caught | admin |
| `test-ssid` | the temporary test network (to come) | admin, operator, installer |
| `sign-ins` | the sign-in record of those holding roles there | admin, manager |

**A test network** (0179) is switched on with a `set` of `test_network.network` and `test_network.until` (Unix seconds) together, on a Locations node: the network a test network (`network.<id>.test`) the folders there offer, until ahead and at most four hours away, or `400`. It takes the `test-ssid` right; unsetting it switches it off.

Giving a role, or taking it, needs admin there; a manager gives and takes `manager`, `installer` and `viewer`. Only an owner makes an owner.

**Signing in** (0176): every request except `/healthz`, `/v1/enroll`, `POST /v1/session` and an invite's `/v1/register` (0336) carries either `Authorization: Bearer <token>` (an account's token, or on the AP routes an AP's) or the session cookie `aeolus_session`.
- **The cookie** comes from signing in with a password, and is `HttpOnly`, `Secure` and `SameSite=Strict`.
- **A change made with the cookie** (any method but `GET`, `HEAD` and `OPTIONS`) must also carry the header `X-Aeolus-Session`, or it is refused `403`.
- **A session ends** after 8 hours unused, or 30 days if kept; and at once when its account is disabled or removed, or its password changed elsewhere.
- **A temporary password:** the session may only `GET /v1/whoami` and `POST /v1/session/password` until the password is changed. Anything else answers `403` with `must_change: true`.
- **Guessing is slowed:** 5 failed sign-ins for an account, or 5 failed sign-ins or tokens from an address, lock it for 1 minute, doubling to at most 15. The lock answers `429` with `Retry-After`.

| Request | Body | Does |
|---|---|---|
| `POST /v1/session` | `{account, password, keep?}` | signs in: sets the cookie, kept 30 days with `keep`, and answers `{account, name, owner, must_change}`. A wrong account and a wrong password both answer `401` "wrong account or password". Every try, and why it failed, is recorded for 90 days |
| `DELETE /v1/session` | | signs out: ends the session and clears the cookie |
| `POST /v1/session/password` | `{current, new}` | sets your own password, 12 to 128 characters and not your account's ID. `current` is needed unless you have none yet. A wrong one answers `403`. Your other sessions end; this one goes on. Answers `{ok, other_sessions_ended}` |
| `GET /v1/register/{code}` | | what an invite gives, for the one it is for (0336): `{org, by, roles, owner, expires, note, password_min}`, each role `{tree, node, role, where}`. The code, the part of the invite's link after `#/register/`, is the credential. A code the manager never made answers `404`, and counts as a failed try from the address, as a wrong password does; one used, revoked or expired, or whose maker is no longer an owner, `410` |
| `POST /v1/register` | `{code, account, name?, password, keep?}` | makes the account the invite is for and signs it in, as `POST /v1/session` does, answering `{account, name, owner, must_change}`. The account is 2 to 32 characters: lower case letters, digits, `.`, `_` or `-`, from a letter; one taken, or one starting `aeolus`, kept for the manager's own, answers `409`. The password follows the rules above, and is its own from the start. The manager makes the change in its own name, `use-invite`, once only; the roles are the invite's |

An `op` is one change, as the change log records it:

```json
{"kind": "set", "tree": "services", "node": "household", "path": "network.sweet.ssid", "value": "Home Wi-Fi"}
```

A `set` can instead carry `values`, several fields of one node set together, all or none, as one logged change (0045):

```json
{"kind": "set", "tree": "locations", "node": "house", "values": {"radio.5g.width": 160, "radio.5g.channel": "auto"}}
```

An `unset` can likewise carry `paths`, several fields of one node unset together. Each must be set there, or none is unset (0046):

```json
{"kind": "unset", "tree": "locations", "node": "ap-a0046082275e", "paths": ["radio.5g.channel", "radio.5g.width"]}
```

A `batch` carries `ops`, 1 to 256 sets and unsets, each with its own `tree` and `node`, made in order as one logged change: all of them or none (0203). Since 0320 it may also carry `add-folder` and `assign-services`, so a new services folder, a location taking it and a network in it are one change. Each is allowed and checked as if made alone; in a batch that makes a folder, each is allowed on what those before it leave, so a change in the new folder is judged where the folder will be, and an error names the one that failed ("change 2 of 2 (…)"). Its effect is each one's, in order, and a preview's `resolved` is a list of each one's `tree`, `node` and fields:

```json
{"kind": "batch", "ops": [
  {"kind": "set", "tree": "services", "node": "household", "path": "network.sweet.ssid", "value": "Home Wi-Fi"},
  {"kind": "unset", "tree": "services", "node": "upstairs", "paths": ["network.sweet.ssid"]}
]}
```

Spanning tree on the bridge the AP's uplink is in is `uplink.stp`, true or false (0095); `uplink.bond` false takes the uplink's LACP bond apart, each of its ports in that bridge on its own, which needs `uplink.stp` true (0096). A kind of AP's own ports are set as `boards.<board>.ports.<name>.<field>` (0092), and its uplink as `boards.<board>.uplink.stp` and `.bond`: an AP of that board takes them in place of the plain `ports.<name>.<field>` set on the same node or above; the manager folds them into the AP's own, so an AP's config never carries `boards.`. A tunnel is set like any Location field (`concentrators.<name>.address`, `.port`, `.mtu`), and so is what a tunnel port carries (0058): `ports.<name>.mode` `tunnel`, and `ports.<name>.vxlan.<vlan>.tunnel` and `.vni` for each VNI, where `<vlan>` is the VLAN it is tagged with on the port, or `untagged`. What the AP's prober does is set the same way (0059): `concentrators.<name>.probe_interval`, and a probe address, `.probe`, on a network's transport and on a tunnel port's VNI. Moving an AP out of Landing Zone (a node with `"isolated": true`) is adoption: it needs viewer on Landing Zone and operator on the destination (0032). `create-org` happens only through `aeolus init` on the manager host, and tokens are issued through `/v1/tokens`. A password is never sent as a change: `set-password` is refused here, and `/v1/changes` never shows a password's hash (0176). Set values are checked against the field schema (`internal/schema/v1.json`), and secret values are sealed before they are logged (0027). Who may make which change is 0030.

Per-user keys (0070) are changes too, but not config: they re-version no AP. `add-key`, `set-key` and `remove-key` take the Services folder that offers the network in `node`, the network in `network`, and the key's ID in `key` (lower-case letters, digits and `-`, at most 32; `add-key` makes one if it is left out). Their `value` is the key, `{name, passphrase, vlan?, macs?, expires?}`:

```json
{"kind": "add-key", "node": "household", "network": "sweet", "value": {"name": "Unit 101", "passphrase": "a passphrase of 8 to 63", "vlan": 101}}
```

- **The passphrase is given in plain text,** checked (8 to 63 printable characters) and sealed before it reaches the log. It must differ from the network's own and from the network's other keys'. `set-key` may leave it out to keep the one it has.
- **`vlan`,** if any, must be one of the network's `keys.vlans`. `macs` binds the key to at most 16 devices. `expires`, if any, must be in the future.
- **The network must be `wpa2-psk`.** A change to the trees that would strand a key (its network gone, its security changed, or its VLAN no longer offered) is refused with 409, naming the keys.
- **Who:** an operator on the folder.

## Installing from the manager

What an AP with nothing of Aeolus fetches, with no token, from the manager it will join (0083): `wget -qO- --no-check-certificate https://<manager>:8443/install | sh`. None of it is secret.

| Request | Returns |
|---|---|
| `GET /install` | the installer, a shell script, with `https://` and the request's Host as the manager's URL; `400` for a Host that is not a DNS name or an address with an optional port |
| `GET /install/manager.crt` | the manager's TLS certificate, PEM, which the AP pins |
| `GET /install/manifest` | `{version, agent, luci}`: the manager's own release, its agent bundle (as `GET /v1/ap/agent` gives one) and LuCI's Aeolus page, a bundle of the same form |
| `GET /install/files/{sha256}` | one of those bundles' files, as it is; `404` for any other |

All four answer `404` from a manager that keeps no agent bundles.

## The feed cache

`GET /feeds/<path>` (0069) is the same file as `https://downloads.openwrt.org/releases/<path>`, through the manager's cache: APs fetch their packages through it. It needs no token, since `apk` can't send one and the files are OpenWrt's own, signed by OpenWrt. It answers only paths in that tree, each part letters, digits and `._+~-`, and only `GET` and `HEAD`.

- **The first request for a file fetches it,** once however many ask at the same time, and keeps it.
- **An index** (`*.adb`, `Packages*`, `sha256sums*`, `*.json`, `*.sig`, `*.asc`) is fetched again when it is more than a day old. If OpenWrt's server doesn't answer, the copy kept is served.
- **Anything else never changes,** and is kept until the cache is full. Then the least recently used goes.
- **A release branch's snapshots** (`25.12-SNAPSHOT/...`) are the exception: they are built anew under the same names, and `apk` refuses a package of another build than its index names. Their index is fetched again after five minutes, not a day, and when it has changed the packages kept beside it go, to be fetched again of the build it names (0171).
- **What it doesn't have and can't fetch:** 502, once connecting has taken 10 seconds or an answer 30. What OpenWrt doesn't have: 404.

`AEOLUS_FEED_CACHE` (default `feeds` beside the change log, `/var/lib/aeolus/feeds`) and `AEOLUS_FEED_CACHE_MB` (default 2048), or `-feed-cache` and `-feed-cache-mb`, place and size it; `off` turns it off.

### Module feeds

`GET /feeds/kmods/<kernel version>/<file>` (0171) is a file of the module feed for that kernel, which the manager keeps: for an image built with a kernel of its own, such as the Arista ports, whose kernel modules fit none of OpenWrt's feeds. The kernel version is the AP's `kernel` package's, such as `6.12.112~1439aebc94b35ebb6258531fbd56aa12-r1`; the files are the feed's `packages.adb` and the packages beside it. Like the cache, it needs no token and answers only `GET` and `HEAD`; a kernel it has no feed for, or any other path, is 404.

- **A feed is a build's own, copied in as it is:** a directory holding a `packages.adb` and `kernel-<version>.apk`, such as the Arista port build's `out/<model>/<version>/feed/packages/`, put anywhere up to four directories below `AEOLUS_KMOD_FEEDS`. Its packages are signed with the build's key, which that build's image trusts; the manager only hands them on.
- **One copied in while the manager runs** is found when an AP first asks for its kernel, at most a minute after the last look.
- **By build too (0260):** `GET /feeds/kmods/<kernel version>/<build tag>/<file>` is a file of that build's feed for that kernel. A feed is of the build whose tag, such as `v2026.10.17.1-83-g439336f`, is in its directory's path below `AEOLUS_KMOD_FEEDS`, as the port's builder names its output (`out/main/v2026.10.17.1-83-g439336f/feed-ipq807x/`). A port image asks for its own build's first, its tag from `/etc/os-release`, and takes its kernel's where the manager has none. Every build of a port can share one kernel, and one build's ucode modules may not fit another's image. By the kernel alone, the newest settled feed for it is served, as before.
- `AEOLUS_KMOD_FEEDS` (default `kmods` beside the change log, `/var/lib/aeolus/kmods`), or `-kmod-feeds`, places them; `off` turns them off.

## The manager's DHCP listeners

Besides the API, the manager listens, without ever answering (0068):

- **UDP port 67, for relays' copies of DHCP requests.** A site adds the manager as an extra helper address on its relays. Only relayed client requests are kept; anything else is counted as ignored.
- **TCP port 15002, for OpenWiFi APs' knocks.** In DHCP scopes an admin chooses, option 224 names the manager. An OpenWiFi AP there connects over TLS; the manager records the connection and closes it. A connection that sends no TLS hello isn't one.

`AEOLUS_RELAY_LISTEN` and `AEOLUS_KNOCK_LISTEN` in `serve.env` (or `-relay-listen` and `-knock-listen`) move them, and `off` turns either off. A listener that can't start is logged, and the API serves without it.

## The manager's name on its own network

The manager answers multicast DNS for `aeolus.local` (UDP port 5353, group 224.0.0.251) on every network it is on, with its own address there, so that an AP with the finder and no DNS to ask finds it (0151). It answers for that one name's IPv4 address and nothing else. `AEOLUS_MDNS` in `serve.env` (or `-mdns`) gives another name, one label, and `off` turns it off. Where it can't start, that is logged, and the API serves without it.

## MCP

`/mcp` serves the API as MCP tools (streamable HTTP): `whoami`, `list_tree`, `get_node`, `get_ap_config`, `get_ap_history`, `get_library`, `get_relayed_dhcp`, `list_detected`, `list_keys`, `list_changes`, `preview_change` and `make_change`. Each request carries the caller's own token, and the tools call the API with it, so changes are logged under the caller's name (0031). `make_change` takes a reason as an optional note (0062).

## Errors

`{"error": "..."}` with `400` (invalid change or value), `401` (no or bad token), `403` (not permitted), `404` (not found or not visible), `409` (conflicts with the current state: a lock, an AP that would stop resolving, something that already exists), `503` (Landing Zone is full).
